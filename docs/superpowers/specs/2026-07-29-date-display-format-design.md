# 日期展示格式统一设计

## 目标

修复小程序和后台管理页面直接展示接口原始 ISO 时间的问题。所有面向用户的日期时间文本统一显示为 `yyyy-MM-dd`，例如：

- `2026-08-28T14:08:47.662+08:00` 显示为 `2026-08-28`
- `2026-08-28 14:08:47` 显示为 `2026-08-28`

本次只调整展示格式，不修改数据库字段、接口时间精度、业务时区、排序条件、有效期计算或定时生效逻辑。

## 根因

后端日期字段按完整时间序列化，部分小程序 WXML 和后台 Vue 表格直接绑定原始字段，没有经过展示层格式化，因此出现带 `T`、毫秒和时区偏移的 ISO 文本。

## 方案

在两个前端分别建立统一的日期展示边界：

- 小程序使用公共 `formatDate` 工具，将接口返回的日期值格式化为 `yyyy-MM-dd` 后再展示。
- 后台管理端复用现有 `parseTime` 能力，并显式传入 `{y}-{m}-{d}` 格式；直接绑定日期字段的表格列改为插槽格式化。
- 后端继续返回完整时间，页面内部需要比较、排序或提交的原始值不截断。

不采用后端全局日期截断，因为这会丢失时分秒并影响会员到期、协议生效、轮播展示和兑换码失效等业务判断。不采用页面内零散字符串截取，避免重复代码和后续遗漏。

## 小程序范围

检查并统一所有实际展示的日期字段，至少包括：

- 会员兑换成功弹窗中的新到期日期。
- VIP 页面和会员套餐页面的会员有效期。
- “我的”页面用户卡片中的会员到期日期。
- 积分流水的发生日期。
- 其他小程序页面中新增或已存在的日期文本绑定。

小程序公共方法的规则：

- 空值返回空字符串。
- ISO、常见日期时间字符串和 `Date` 可解析值统一输出 `yyyy-MM-dd`。
- 对带时区的 ISO 字符串优先取其原始年月日部分，避免运行环境时区转换导致日期前后偏移。
- 无法识别的非空值保留原值，避免页面无提示地丢失服务端数据。

服务层可对纯展示资料进行格式化；仍参与业务判断的时间值保留原始字段，页面只在渲染前生成展示值。

## 后台管理范围

排查 `ruoyi-ui/src/views/library` 下所有业务页面的日期展示，至少包括：

- 微信用户列表、详情中的会员到期日期和最后登录日期。
- VIP 权益台账中的原到期日期和新到期日期。
- VIP 兑换码、课程兑换码的使用日期和过期日期。
- 协议的生效日期。
- 宣传图片的开始日期和结束日期。
- 订单、退款、授权、文档等页面中实际展示的日期字段。

后台已有若依基础页面继续复用现有时间工具；本次重点修复项目自有 `library` 业务页面及小程序页面，避免改动全局默认格式而影响框架组件、日志和第三方页面。

日期输入控件仍保留原来的日期时间选择能力，编辑回显和提交继续使用完整值；仅列表、详情、卡片、弹窗提示等只读文本显示年月日。

## 数据流

1. 后端按现有格式返回完整日期时间。
2. 前端保留原始数据供比较、排序、编辑和提交。
3. 展示层调用统一格式化方法生成 `yyyy-MM-dd` 文本。
4. 空日期继续显示页面原有的“未开通”“长期有效”或 `-` 等占位文案。

## 异常处理

- 空值不生成 `Invalid Date`。
- 无法解析的值不参与日期计算；展示格式化不得抛出异常。
- 日期格式化失败时保留原始文本，便于发现异常数据。
- 会员是否有效仍依据完整时间判断，不能依据截断后的日期判断。

## 验证

- 为小程序公共日期方法增加测试，覆盖 ISO 时区字符串、普通日期时间、纯日期、空值和非法值。
- 验证会员兑换成功弹窗、VIP 页面、会员套餐页面和“我的”页面只显示年月日。
- 验证积分流水日期只显示年月日。
- 验证后台 `library` 业务页面不存在直接展示原始日期字段的遗漏。
- 验证会员状态、到期计算、表格排序和日期时间表单提交仍使用完整时间。
- 运行相关小程序测试和后台前端构建或针对性静态检查；不处理与本次日期展示无关的既有失败。

## 不在本次范围

- 不修改数据库结构或历史数据。
- 不修改后端日期序列化全局配置。
- 不改变业务时区。
- 不改变会员、兑换码、协议或宣传图片的生效和失效规则。
- 不修改若依框架内与 `library` 业务无关的系统管理、监控和代码生成页面。
